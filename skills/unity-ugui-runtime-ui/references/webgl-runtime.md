# webgl-runtime.md

Unity（WebGL）でuGUI画面を実行するときの、解像度・アスペクト比追従、入力方式、性能、WebGLブラウザ差に関する判断基準を与える。

**読み込み条件**（`SKILL.md`「参照ファイルの読み込み条件」）：一覧が50件を超えるとき、性能・入力方式の要求があるとき。

本ファイルは`SKILL.md`本文の不変条件（12項目）を前提とし、それらを緩めない。特に以下と関わる：
不変条件2（`EventSystem`と入力モジュール）・3（`CanvasScaler`・`GraphicRaycaster`）・4（LayoutGroupの子に`ContentSizeFitter`を付与しない）・
5（ScrollRectの構成）・6（生成参照はフィールドで保持し名前検索で取り直さない）・9（色・寸法・文字サイズ・文言はテーマまたは定数に集約）。

対象外：UI Toolkit（`requirements.md` 2.2節）。加えて本ファイル独自の判断として、ネイティブアプリ固有の入力（マルチウィンドウ、OSレベルのショートカット）、ネットワーク同期も扱わない。

## 1. 解像度・アスペクト比追従

### 1.1 基本方針（`SKILL.md`本文の再確認）

- `CanvasScaler`は`ScaleWithScreenSize`、参照解像度は前提セットの値（既定1920×1080）、`matchWidthOrHeight`は横長で0.5・縦長で0とする（不変条件3・F2手順7）。
- WebGLはウィンドウのリサイズ・ブラウザのズーム・デバイスのDPRによって`Screen.width`／`Screen.height`が実行中に変化する。追従はCanvasScalerに委ね、個々のコンポーネントで解像度を読んでピクセル値を計算し直さない。

### 1.2 極端なアスペクト比

| 比率 | 想定要因 | 判断 |
|---|---|---|
| 21:9・32:9（超横長） | ウルトラワイドモニタ、ブラウザの分割表示 | 中央コンテンツは最大幅コンテナ（1.3節）で頭打ちにする。背景・装飾のみ両端まで伸ばす。 |
| 9:16（縦長） | モバイルブラウザの縦持ち | `matchWidthOrHeight = 0`（幅基準）により、縦方向の要素が画面外へ伸びやすい。縦に並ぶ一覧・フォームはScrollRect化を優先する（アンカー固定を避ける）。 |
| 4:3・5:4（横長だが低い） | 古いモニタ、ブラウザウィンドウの縮小 | 横方向の余白が縮み、横並びのボタン群が重なりやすい。HorizontalLayoutGroupに`LayoutElement.flexibleWidth`を与え、必要なら折り返し（GridLayoutGroupへの切替）を検討する。 |

これら4種の比率は`UiResolutionSweepTests`（16:9・4:3・21:9・9:16）の検証対象と一致させる（5.6節・7.4節）。設計時点でこの4比率を暗算し、はみ出す要素がないかを確認する。

### 1.3 中央コンテンツの最大幅コンテナ

- 端に寄せる要素（ヘッダー・フッター・サイドパネル）はアンカーで画面端に固定する。
- 中央の主要コンテンツ（本文・フォーム・カード一覧）は、`LayoutElement.preferredWidth`または`RectTransform`の`sizeDelta`で最大幅（例：`UiTheme.Sizes`に`ContentMaxWidth`を定義）を与え、それを超える横幅では左右に余白を作る。ウルトラワイドで文字列が不自然に伸びるのを防ぐ。
- 最大幅コンテナの値もリテラルではなく`UiTheme`に集約する（不変条件9）。

### 1.4 複数解像度でのテキスト折り返し確認

- `Text.horizontalOverflow`は`Wrap`を既定とし、`Overflow`はボタン内の短いラベルなど折り返し不可能な場合に限定する。
- 縦長・低横幅の比率では、日本語のような分かち書きしない言語は任意の文字位置で折り返される。長い文言はボタン・タブなど幅が固定される要素に置かない。
- `Text.preferredWidth`が確保領域を超える場合、`UiResolutionSweepTests`が検出する（5.6節手順3）。設計段階では、想定される最長文言（多言語対応時は翻訳後に伸びる言語を含む）で目視確認する。

## 2. 入力方式

前提セットの入力方式（F1手順6の既定：マウス＋タッチ、キーボードは要求時のみ）に応じて、以下の判断を行う。ゲームパッドは既定に含まれないため、要求された場合のみ2.4節を適用する。

### 2.1 マウス

- WebGLではブラウザごとにホイールの`scrollDelta`の単位・符号が異なる（行単位・ピクセル単位が混在する）。`ScrollRect.scrollSensitivity`は固定値をそのまま使わず、`UiTheme`に定数化した上で、極端に速い・遅いブラウザがあることを前提に、値を大きく振らない範囲（既定を基準に0.5〜2倍程度）で調整する。
- ホバー表現（色変化等）はマウス環境でのみ意味を持つ。タッチ環境では`PointerEnter`がクリック直前にしか発火しないため、ホバーのみに依存した状態表示をしない（押下遷移で代替する。F2手順5）。

### 2.2 タッチ

- WebGLの`Input.touchSupported`はデスクトップブラウザで`false`、モバイルブラウザで`true`になるが、モバイルブラウザでもマウスイベントとして扱われる場合がある。マウス専用・タッチ専用の分岐を作らず、`EventSystem`の標準入力モジュール（`StandaloneInputModule`、またはInput System採用時は`InputSystemUIInputModule`）が両方を吸収する構成のみを前提にする（`UiFactory`のテンプレートコメントに準拠）。
- タップ領域44px以上（不変条件10）は、モバイルブラウザの実タップ精度（指先は44pxより広い接触面を持つ）を踏まえた下限であり、これを下回る調整をしない。
- ピンチズーム・スワイプ等のマルチタッチジェスチャーは本ファイルの対象外とする（著者判断）。ScrollRectの単一指スクロールのみを前提にする。

### 2.3 キーボード

- キーボード操作が要求される画面では、`Selectable.navigation`を`Explicit`にし、`selectOnUp`／`selectOnDown`／`selectOnLeft`／`selectOnRight`を明示する（F2手順6、不変条件に準ずる判断）。自動（`Automatic`）は矩形の位置関係のみから推測するため、WebGLの可変解像度では狙った順序にならないことがある。
- CJK文字を入力する`InputField`は、WebGLブラウザ側のIME（変換候補ウィンドウ）表示がブラウザ実装に依存し、候補ウィンドウの位置がCanvas上のフィールド位置と一致しない場合がある。これはC#側の実装で解決できないため、既知の制限として報告する（F6手順5）。
- ブラウザの既定動作（Tabキーによるブラウザ内フォーカス移動、Spaceキーによるページスクロール）とゲーム内のキーボード操作が衝突することがある。回避はUnity側のWebGLテンプレート（`index.html`）の領域であり、本ファイルの対象外とする（著者判断）。既知の制限として報告する。

### 2.4 ゲームパッド

- WebGLのGamepad API対応はブラウザ間で差があり（接続検出のタイミング、ボタン割り当て）、常時動作する前提を置かない。
- ゲームパッド操作が要求された場合でも、マウス・タッチ・キーボードのいずれかで全操作が完結する構成を維持する（ゲームパッド専用の操作を作らない）。
- 前提セットにゲームパッド要求がある場合、F1で「WebGLでの動作保証外」である旨を出所「既定」として明記する。

### 2.5 入力方式の前提確認

- 入力方式は前提セット（F1）の項目であり、本節はその判断材料を与えるのみで前提収集手順そのものを変更しない。要求文に入力方式の明示がなければ、F1既定（マウス＋タッチ）を用いる。

## 3. 性能

### 3.1 Canvas再構築の最小化

- uGUIは`RectTransform`の変更・`Graphic`の有効化無効化・LayoutGroupの再計算のたびに、対象Canvasのサブツリー全体を再構築（レイアウト再計算・再バッチ）する。頻繁に変化する要素（カウンタ表示、進行中アニメーション、頻繁な状態遷移を持つHUD等）は、静的な要素と同じCanvasに置かず、専用の子Canvasに分離し、再構築の範囲をその子Canvasに閉じ込める。
- 子Canvasを増やすこと自体にもオーバーヘッドがある（3.2節のバッチング分断）。分離は「頻繁に変わる領域」対「ほとんど変わらない領域」の境界でのみ行い、要素単位の細分化はしない。
- `Render(state)`（F3手順2）は、状態が変化した場合にのみ実際の値変更を行う。値が変わっていないのに同じ文字列・色を毎フレーム再設定しない（`Text.text`への代入はレイアウト・再描画のダーティフラグを立てるため、変化がない代入も避ける）。
- LayoutGroupは子オブジェクト数に比例して計算コストが増える。3.3節のプール対象のように子数が多い一覧では、LayoutGroupの自動計算を常時有効にしない（3.3節参照）。
- 初期構築（`Build`）で一度に大量の要素を生成すると、その1フレームが長くなり、WebGLでは特にメインスレッドがブロックされる。50件を超える初期表示が必要な場合は3.3節のプールを前提にし、全件を一括生成しない。

### 3.2 バッチング

- 同一マテリアル・同一テクスチャ（アトラス共有）のUI要素はバッチ結合される。`UiFactory`が供給する9分割スプライト（角丸・枠線、7.4節）は手続き的に生成するため、画面内で同じ見た目の枠には同じ生成結果（同一テクスチャ）を使い回し、見た目が同じ要素ごとに個別のテクスチャを生成しない。
- `Text`（`UnityEngine.UI.Text`）はフォントごとにマテリアルが分かれる。1画面で使うフォントの種類を`UiTheme`に集約された最小限に保つ（本文用・見出し用の2種程度）ことで、バッチが分断されにくくなる。TextMeshProを使う場合も同様に、フォントアセットの種類を増やさない。
- `RectMask2D`・`Mask`はバッチを分断する要素の一つ。ScrollRectのViewportは構成上必須（不変条件5）だが、それ以外の箇所でマスクを多用しない。
- 半透明（アルファ）を持つImageの重なりはオーバードローを増やす。背景の上に半透明パネルを何層も重ねる設計を避ける。

### 3.3 50件超の一覧：行プール設計

件数が不明、または50件を超えることが想定される一覧（F3手順4で要求される設計）は、以下の方針で行プールを設計する。

**構造**：ScrollRectの構成（Viewport＋RectMask2D → Content＋LayoutGroup＋ContentSizeFitter）自体は不変条件5どおりに保つ。ただし、Content配下に実データ件数分の行を生成せず、画面に収まる行数＋予備分のみを生成して使い回す。

**プールサイズの算出**：

```
必要プール数 = ceil(Viewportの高さ / 1行の高さ) + 予備2行
```

予備2行は、スクロール中に行の一部が可視範囲の直前・直後に差し掛かる分の余裕である。行の高さ・余白は`UiTheme.Sizes`の値を用い、リテラルを直接計算式に書かない。

**運用**：

1. `Build`でプールサイズ分の行オブジェクトを1回だけ生成し、参照を配列またはリストのフィールドで保持する（不変条件6）。生成後に`GameObject.Find`・`transform.Find`で取り直さない。
2. Contentの高さは、実データ件数から計算した仮想高さ（`件数 × 1行の高さ + 間隔 × (件数 - 1) + 上下パディング`）を用いる。件数分の実オブジェクトを配置しない構成のため、`ContentSizeFitter`とLayoutGroupの自動計算だけでは仮想高さを再現できない場合がある。その場合はLayoutGroupを生成直後の初期配置にのみ使い、以降は無効化（`enabled = false`）した上でContentの`sizeDelta`を仮想高さで直接設定し、各行の`anchoredPosition`をスクロール位置から算出したインデックスに応じて再配置する。LayoutGroup・ContentSizeFitterのコンポーネント自体は取り外さず、構成としては維持する（不変条件5との整合、および静的検査での必須構成検出を妨げないため）。
3. `ScrollRect.onValueChanged`で現在の可視範囲（先頭インデックス〜末尾インデックス）を計算し、範囲外になった行だけを次に必要なデータへ更新する（`Render`相当の処理を行単位で行う）。全行を毎回更新しない。
4. 行の見た目更新（テキスト・アイコン・状態表示）は3.1節の方針に従い、値が変化した場合のみ行う。
5. 状態一覧（F2手順4）の「空」「読込中」はプールされた行とは別に、Content外またはContentの先頭に固定表示するプレースホルダで扱う。行プールの空データ（0件）表示に流用しない。

**50件以下の一覧**：プール化による複雑さは50件超で初めて見合う。50件以下は素直に全件をContent直下へ生成し、LayoutGroup＋ContentSizeFitterの自動計算に任せてよい（F3手順4の「件数が不明または50件を超える」に該当しない場合）。

## 4. WebGLブラウザ差

### 4.1 メモリ制約

- WebGLビルドのヒープサイズはビルド設定側の値であり、実行時コードからは変更できない（本スキルの対象外の設定）。実行時コード側で行うべきことは、不要なメモリ確保を避けることに限られる。
- `Update`・`LateUpdate`・`Render`内での文字列連結、`foreach`によるボックス化、LINQの使用は、毎フレームのガベージコレクション（GC）割り当てを生む。GC発生時にWebGLはメインスレッドが一時停止し、フレーム落ちとして体感される。一覧の行更新（3.3節）・状態遷移（`Render(state)`）はこの割り当てが起きやすい箇所であるため、キャッシュ済みの`StringBuilder`や、変化がない場合は処理そのものをスキップする設計にする。
- モバイルブラウザは特にメモリ上限が低い。9分割スプライト（角丸・枠線）を都度生成し直さず、同一の見た目は生成結果を使い回す（3.2節）。

### 4.2 フォーカス・可視性挙動

- ブラウザタブがバックグラウンドになると、`requestAnimationFrame`が抑制または停止され、Unityのフレーム更新が止まる、または大きく間引かれる。復帰時に`Time.deltaTime`が異常に大きい値になることがあるため、アニメーション・タイムアウト処理は`deltaTime`を上限でクランプするか、経過時間ではなく状態遷移で管理する。
- `Application.runInBackground`はWebGLでは効果が限定的（ブラウザのタブスロットリングが優先される）。バックグラウンド前提の処理（自動保存・通信のリトライ）をUIの更新ループに依存させない。
- フォーカスが外れている間に破壊的操作の確認モーダル（F2手順5）が表示されたままになるケースを考慮し、モーダルは復帰後も状態を保持し、二重送信を防ぐ（ボタンの多重クリック防止と合わせて設計する）。

### 4.3 その他のブラウザ差

| 項目 | 差異 | 判断 |
|---|---|---|
| フルスクリーンAPI | ユーザー操作（クリック等）を伴わない呼び出しは拒否される | フルスクリーン切替はボタンの`onClick`ハンドラ内から直接呼び出す。遅延実行（コルーチン経由等）にしない。 |
| ファイル入出力 | ネイティブのファイルダイアログ・ローカル保存はWebGLでは制限される | ダウンロード・アップロードを伴うUIは対象外として扱い、要求された場合は範囲外の所見として報告する。 |
| DPR（デバイスピクセル比） | Retina等高DPR環境で`Screen.width`の解釈がブラウザにより異なることがある | CanvasScalerの追従（1.1節）に委ね、DPRを個別に読んで補正計算をしない。 |
| ブラウザの拡大縮小（Ctrl+ホイール等） | ページ全体がズームされ、Canvasの実効解像度が変わる | 1.2節の極端なアスペクト比・低解像度側と同じ設計（最大幅コンテナ・ScrollRect化）で吸収する。専用の分岐を作らない。 |

## 5. 検証との対応

- 本ファイルで扱う判断は、F5検証手順（5.6節）の一部と対応する。特に3.3節の行プール設計は`UiResolutionSweepTests`のタップ領域下限割れ検査、1.2節の極端なアスペクト比は同テストの画面外はみ出し検査と対応する。
- 性能（3章）・ブラウザ差（4章）はUnity CLIの`-batchmode -nographics`実行では検出できない項目（実ブラウザでのフレーム落ち、GCポーズ、フォーカス挙動）を含む。検証段階が静的検査またはCLI段階に留まる場合、これらは「未検証」として報告する（F6手順5、不変条件12）。実ブラウザでの確認は範囲外の所見として扱い、実施済みとして報告しない。
