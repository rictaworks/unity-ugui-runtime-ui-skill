# review-rubric.md — レビュー観点と重大度の判定基準

`SKILL.md` F7（レビューモード固有手順）から読み込む。既存のuGUI関連C#を本ファイルの観点表と照合し、所見を3段階の重大度に分類する。読み込み条件：レビューモードの常時（`SKILL.md`「参照ファイルの読み込み条件」表）。

構築・改修モードでも、F3手順8（改修モードでの変更範囲外の扱い）やF6の報告に「所見」を記す場面では本ファイルの重大度基準を流用してよい。

---

## 1. 所見の3段階と判定基準

`SKILL.md` F7手順2の3段階を、判定できる基準まで分解する。1件の所見は必ずこのいずれか1段階に属する。複数の段階にまたがるように見える所見は、最も重い段階1つに分類し、軽い側の影響は同じ所見の記述に含める（所見を分割しない）。

| 段階 | 判定基準 | 典型例 |
|---|---|---|
| **重大** | 画面が表示されない、操作できない、コンパイルが通らない、CJK文字が表示されない（豆腐化・欠落）など、利用者が機能を使用できない状態を指す。不変条件1〜8・12の違反はこの段階になりやすい。 | `EventSystem`未生成でクリックが一切反応しない／`CanvasScaler`未設定で解像度によって画面が消える／`GameObject.Find`の失敗によりnull参照例外／CJKフォント未同梱で本文が空白 |
| **改善** | 画面は表示・操作できるが、使いにくい、崩れる、アクセシビリティ基準を満たさないなど、体験の質を損なう状態を指す。不変条件9〜11の違反、UX項目（3章）の未達はこの段階になりやすい。 | タップ領域が44px未満／コントラスト比が4.5未満／状態一覧のうち「空」表示が無くデータ0件で真っ白になる／破壊的操作に確認が無い／戻る手段が無い |
| **提案** | 現状は動作し体験も損なわないが、保守性・拡張性を下げている状態を指す。4章（保守性）の未達はこの段階になりやすい。 | 色リテラルの直書き（動作はするがテーマに未集約）／`Build`と`Render`の責務混在／命名規約からの逸脱／テンプレートを踏襲しない独自実装 |

**判定の要点**

- 「動作するか／しないか」がまず重大と改善・提案を分ける境界であり、「体験を損なうか／損なわないか」が改善と提案を分ける境界である。
- 不変条件（6章／2章）への違反は原則として重大または改善に分類し、提案には分類しない。不変条件は`references`を読まなくても`SKILL.md`本文で守られるべき最低限であるため、違反は保守性の問題ではなく機能・体験の問題として扱う。
- 判定に迷う場合は重い側に分類し、根拠に判断の分かれ目を明記する。

## 2. 観点表：不変条件（12項目）

`SKILL.md`「設計原則（不変条件）」の12項目に対応する。項目番号は`SKILL.md`と一致させる。

| # | 不変条件 | 既定の重大度 | 検出方法 |
|---|---|---|---|
| 1 | 実行時コードに`UnityEditor`名前空間・`OnGUI`・`AssetDatabase`を含めない | 重大（WebGLビルドで消失・コンパイル不能） | `lint_ugui_csharp.py`の`unity_editor_namespace`・`ongui_definition`・`asset_database_usage` |
| 2 | シーンに`EventSystem`と入力モジュールを1つ用意する（無ければ生成） | 重大（未生成時：全操作が反応しない） | `lint_ugui_csharp.py`の`event_system_missing`（走査対象全体でCanvas生成があるのに`EventSystem`生成が無い） |
| 3 | 各Canvasに`CanvasScaler`（`ScaleWithScreenSize`）と`GraphicRaycaster`を付与する | 重大（`CanvasScaler`欠落：解像度追従が破綻）／改善（マッチ値が横長0.5・縦長0の既定から外れているのみ） | `lint_ugui_csharp.py`の`canvas_scaler_missing`。マッチ値・`ScaleMode`は目視確認 |
| 4 | LayoutGroupの子に`ContentSizeFitter`を付与しない。子の寸法は`LayoutElement`で与える | 改善（レイアウト崩れ・意図しない伸縮） | `lint_ugui_csharp.py`の`layout_group_child_content_size_fitter` |
| 5 | ScrollRectはViewport（`RectMask2D`）とContent（LayoutGroup＋`ContentSizeFitter`）の構成で組む | 重大（構成欠落によりスクロールが機能しない・全要素が見える状態になる）／改善（構成はあるが件数超過時にプールが無く性能が劣化する場合） | 目視確認（`components.md`のScrollRect構成と突き合わせ）。50件超の一覧はプール設計の有無も確認 |
| 6 | 生成した要素の参照はフィールドで保持し、名前検索で取り直さない | 重大（シーン構成変更や多言語化時に`Find`が失敗しnull参照になる） | `lint_ugui_csharp.py`の`find_reacquisition` |
| 7 | CJK文字を表示する場合、対応フォントが`Resources/`またはTMPフォントアセットとして存在しなければ停止する。組み込みフォントで代替しない | 重大（該当文字が表示されない） | `Resources/`配下のフォントファイル・TMPフォントアセットの有無を確認。`text-and-fonts.md`参照 |
| 8 | TextMeshProのフォントアセットを生成しない。既存アセットがある場合に限りTMPを用いる | 重大（フォントアセット無しでTMP参照時に文字が表示されない）／提案（TMP使用条件を満たすのに`UnityEngine.UI.Text`のまま統一されていない） | 既存TMPフォントアセットの有無とテキスト方式の一致を確認 |
| 9 | 色・寸法・文字サイズ・文言はテーマまたは定数に集約する | 提案（動作・体験は保たれるが保守性が下がる） | `lint_ugui_csharp.py`の`raw_color_literal`。寸法・文言のリテラルは目視確認 |
| 10 | 押下可能要素はタップ領域44px以上（参照解像度基準）、コントラスト比4.5以上、状態は色以外でも区別する | 改善（基準未達だが操作自体は可能） | `check_contrast.py`でテーマの前景・背景を検査。タップ領域は`RectTransform`のサイズを参照解像度換算で確認 |
| 11 | 改修モードでは要求範囲外を変更せず所見として報告する | 改善（範囲外の意図しない変更が既存動作に影響する場合）／提案（範囲外だが実害の無い変更） | 変更差分と要求文を突き合わせ、要求に無いファイル・メソッドへの変更を洗い出す |
| 12 | 実施していない検証を実施済みとして報告しない | 重大（未実施のCLIコンパイル・解像度スイープを実施済みと報告し、利用者が誤った前提で判断する） | 報告書の「検証段階と結果」と実際の実行ログ・`UNITY_PATH`の有無を突き合わせる |

## 4. 観点表：保守性

不変条件・UX項目のいずれにも該当しないが、変更・拡張のしやすさに関わる観点。すべて提案として扱う（動作・体験に影響しないため）。ただし放置すると将来的に不変条件違反やUX未達を誘発する所見は、その旨を根拠に書き添える。

| 項目 | 判定基準 | 参照 |
|---|---|---|
| Build/Render分離 | 階層生成（`Build`、1回のみ）と状態反映（`Render(state)`、何度でも）が分離されているか。`onClick`登録が`Build`で1回のみ行われ`Render`で再登録されていないか | `SKILL.md` F3手順2・F4手順5 |
| テンプレート踏襲 | `UiTheme`・`UiFactory`・`UiScreenBase`の既存資産を使わず独自実装が重複していないか。既存規約がある場合にそれへ合わせているか | `SKILL.md` F1手順3・F4手順1 |
| 命名規約 | 画面クラスが`<ScreenName>Screen`等、プロジェクトの既存命名規約に沿っているか | `SKILL.md` F1手順3 |
| 状態網羅 | `Render(state)`が状態一覧のすべてを扱い、未定義状態が例外でなく「空」表示に倒れているか（動作継続の観点で提案とするが、未定義状態で例外を投げる実装は重大に格上げする） | `SKILL.md` F4手順4 |
| ファイル配置 | `assets/`テンプレート起点の配置・命名から外れていないか。既存規約がある場合にそれと矛盾していないか | `SKILL.md` F4手順1 |
| 変更差分の局所性 | 改修モードで、変更が要求に関係するファイル・メソッドに閉じているか（不変条件11に違反しない範囲での、差分の読みやすさ） | `SKILL.md` F3手順8 |
| コンポーネント構築の落とし穴 | ScrollRect・Dropdown・InputField・Slider・Toggle固有の既知の落とし穴（プレハブ化忘れ・イベント多重登録等）を踏んでいないか | `components.md` |
| 性能・入力方式 | 50件超の一覧で行の使い回し（プール）が設計されているか。WebGL固有の入力方式・性能上の既知の制約に反していないか | `webgl-runtime.md`・`SKILL.md` F3手順4 |

## 5. 所見の書き方

`SKILL.md` F7手順3のとおり、修正方針は1所見1方針とし、コードの全面書き換えを提案しない。1件の所見は次の3要素を持つ。

1. **重大度**：1章の3段階のいずれか1つ。
2. **根拠**：該当ファイル・行（または該当箇所）と、2〜4章のどの観点表の項目に基づくかを示す。判定が重い側・軽い側のどちらに寄るか迷った場合は、その判断理由も添える。
3. **修正方針**：該当箇所に閉じた具体的な直し方を1つ示す。「作り直す」「全面リファクタリングする」等、範囲不明の方針は書かない。複数の直し方が考えられる場合は最小の変更で不変条件・UX項目を満たす方針を1つ選ぶ。

同一原因から複数の症状が生じている場合（例：`UiTheme`未使用が色・寸法・文字サイズの3箇所に波及している）は、原因単位で1所見にまとめ、症状は根拠の中に列挙する。所見を症状の数だけ分割しない。
